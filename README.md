# Film Finder Bot

Телеграм-бот с каталогом фильмов по подписке. План работ — в [ROADMAP.md](./ROADMAP.md).

## Деплой

Пошаговая инструкция — [DEPLOY.md](DEPLOY.md). Ниже — как это устроено.

### Render

Бот работает на long polling, поэтому на Render это **Background Worker**, а не
Web Service: не нужны ни домен, ни TLS, ни вебхук. Сервис описан в `render.yaml`,
база и Redis берутся снаружи — Neon и Upstash, у обоих есть бесплатные тарифы,
а свои Postgres и Key Value на Render платные.

При старте бот сам применяет миграции и заводит справочники (жанры, стартовые
тарифы) — оба шага идемпотентны, на существующей базе они ничего не меняют.
Поэтому после деплоя руками делать нечего.

**Почему не бесплатный тариф Render.** Free web service засыпает через 15 минут
простоя, а background worker на free вообще не запускается. Спящий бот — это
не только «не отвечает»: встают фоновые задачи. Выданные фильмы не удалятся
в свои 47 часов (после 48 Telegram их уже не удалит **никогда**), подписки не
закроются по сроку, напоминания и рассылки не уйдут.

Если всё-таки нужен нулевой бюджет: free web service + `WEBHOOK_URL` + внешний
пингер `/healthz` раз в 5 минут — сервис не засыпает и задачи идут как обычно.
Схема рабочая, но держится на трёх бесплатных тарифах сразу.

**Рядом с другим ботом.** На одном аккаунте Render сервисов сколько угодно —
это отдельный воркер, он никак не пересекается с вашим вторым ботом.
Redis можно переиспользовать общий: все ключи здесь идут с префиксом `ff:`
(см. `src/lib/redis.ts`), столкнуться с чужими они не могут. А вот база нужна
своя — таблицы называются обычно (`users`, `films`), в общей они бы столкнулись.

**Регион** — `frankfurt`, ближайший к России и СНГ. Базу и Redis тоже стоит
брать во Франкфурте: каждый лишний океан между сервисом и базой это задержка
на каждом запросе.

### Вебхук или polling

По умолчанию — long polling: ничего настраивать не нужно, публичный адрес не
требуется. Задайте `WEBHOOK_URL` — и бот переключится на вебхук: сам вызовет
`setWebhook` и поднимет HTTP-сервер.

Вебхук нужен там, где хостинг требует занятый порт (Render Web Service,
Railway, Fly), и он дешевле по ресурсам: Telegram стучится сам, а не бот
опрашивает его в цикле.

Адрес вебхука и `secret_token` выводятся из токена бота (SHA-256, первые
32 символа) — отдельной переменной для этого нет намеренно: угадать путь
нельзя, а лишняя обязательная настройка — лишний повод уронить деплой.

Переключение в обе стороны безопасно: перед polling бот снимает оставшийся
вебхук, иначе `getUpdates` отвечал бы ошибкой 409.

`GET /healthz` отвечает `{"ok":true,"uptime":N}`. В режиме polling сервер
поднимается только если задан `PORT`.

### Свой сервер (Docker)

```
docker compose up -d --build
```

Поднимутся три контейнера: бот, Postgres и Redis. Образ бота собирается в два
этапа — в финальный не попадают ни исходники, ни devDependencies, ни компилятор.
PID 1 — `tini`, иначе `SIGTERM` не дошёл бы до приложения и graceful shutdown
не отработал бы.

Бэкапы — `scripts/backup.sh`, в крон:

```
0 4 * * * /opt/film-finder/scripts/backup.sh >> /var/log/film-finder-backup.log 2>&1
```

Держит последние 14 дампов и проверяет каждый на целостность: пустой или
обрезанный архив хуже отсутствующего — он выглядит как бэкап.

### Когда что-то ломается

Бот пишет администраторам сам: при необработанной ошибке в обработчике и перед
падением процесса (`uncaughtException`, `unhandledRejection`). Одинаковые
ошибки схлопываются на 15 минут по отпечатку текста — упавший в цикле
обработчик не должен превратиться в тысячу сообщений и бан за флуд.

Ошибки Telegram API и сети в алерты не идут: они случаются у всех и лечатся
сами, а сообщение о каждой быстро приучает их игнорировать.

```bash

```

### Почему Postgres на 5433

Порт 5432 занят другой установкой PostgreSQL (EnterpriseDB 15). Чтобы не
трогать её, brew-овский `postgresql@14` переведён на **5433**
(`/opt/homebrew/var/postgresql@14/postgresql.conf`, рядом лежит бэкап
исходного конфига).

База и роль созданы так:

```sql
CREATE ROLE filmfinder LOGIN PASSWORD 'filmfinder' CREATEDB;

-- ВАЖНО: локаль обязательно UTF-8, не C.
-- Кластер brew создан с LC_CTYPE=C, а в такой локали pg_trgm не строит
-- тригаммы для кириллицы: show_trgm('матрица') возвращает {} и поиск по
-- русским названиям молча не работает. Поэтому база создаётся отдельно
-- от template1, с явной локалью.
CREATE DATABASE filmfinder
  OWNER filmfinder TEMPLATE template0 ENCODING 'UTF8'
  LC_COLLATE 'en_US.UTF-8' LC_CTYPE 'en_US.UTF-8';

CREATE EXTENSION pg_trgm;    -- поиск с опечатками
CREATE EXTENSION unaccent;
```

Проверить, что поиск с опечатками жив:

```sql
SELECT similarity('интерстелар', lower('Интерстеллар'));  -- должно быть ~0.79, не 0
```

Подключиться руками: `psql -h localhost -p 5433 -U filmfinder -d filmfinder`

### Redis

У локального Redis задан `requirepass`, поэтому пароль входит в `REDIS_URL`:
`redis://default:<пароль>@localhost:6379`. Сам пароль лежит в
`/opt/homebrew/etc/redis.conf`.

Проверка: напишите боту `/ping` — он ответит вашим id и аптаймом.

### Поиск

У `films` есть generated-колонка `search_vector`: Postgres пересчитывает её
сам при каждой вставке и апдейте, поэтому разъехаться с названием она не может.
Поиск идёт двумя путями одновременно, оба через GIN-индексы:

| Путь | Что ловит | Пример |
|---|---|---|
| `search_vector @@ plainto_tsquery('russian', …)` | словоформы | «кольцо» → «Властелин **Колец**» |
| `lower(title) % lower(…)` (pg_trgm) | опечатки | «интерстелар» → «Интерстеллар» |

Русское название весит больше оригинального (`setweight` A против B).

После любого переезда базы или смены локали прогоняйте `npm run db:check` —
в локали `C` расширение `pg_trgm` молча перестаёт работать с кириллицей.

## Устройство бота

Апдейт проходит слои в таком порядке:

```
update
  ↓ requestLogger
  ↓ channelHandler   посты из канала-хранилища — до сессии: у них нет отправителя
  ↓ session          состояние в Redis, ключ по пользователю (ff:session:<id>)
  ↓ auth             upsert в users, кладёт ctx.user и ctx.isAdmin,
  ↓                  забаненных дальше не пускает
  ↓ rateLimit        20 действий за 10 с; админы и платежи не ограничиваются
  ↓ resetOnCommand   команда сбрасывает незавершённый ввод мастера
  ↓ handlers         start → admin → catalog → subscription → payments →
  ↓                  sponsor → menu → search (последний: ловит любой текст)
  ↓ fallback         ответ на кнопку из устаревшего сообщения
```

Порядок не случаен: `rateLimit` стоит после `auth`, потому что ему нужен
`ctx.isAdmin`; `search` — последним, потому что он подхватывает любой
неразобранный текст; `pre_checkout_query` и `successful_payment` проходят мимо
лимита частоты, иначе отброшенный апдейт означал бы сорванную оплату.

### Диплинки

| Ссылка | Что делает |
|---|---|
| `t.me/бот?start=ref_<id>` | записывает пригласившего; повторный переход реферера не меняет, самоприглашение отклоняется |
| `t.me/бот?start=film_<id>` | откроет карточку фильма (этап 4) |

### Проверка без Telegram

`npm run bot:check` собирает настоящего бота, перехватывает исходящие вызовы
и прогоняет через него синтетические апдейты. Наружу не уходит ни одного
запроса, но проверяются реальные сессии, реальная запись в БД и реальный
счётчик лимитов. Тестовые записи скрипт убирает за собой.

## Добавление фильмов

```
Вы заливаете фильм в канал-хранилище (со своего аккаунта, до 2 ГБ)
   ↓ бот — админ канала, ловит channel_post
   ↓ запоминает chat_id + message_id + file_id, заводит черновик
   ↓ пишет вам в личку: «Новый файл. Оформим?»
   ↓ [Оформить] → присылаете название
   ↓ бот ищет в TMDB, показывает до 5 вариантов
   ↓ выбираете → подтягиваются постер, год, описание, рейтинг, жанры
   ↓ [Опубликовать] → фильм виден пользователям
```

Ключевые решения:

- **Координаты сообщения важнее `file_id`.** Выдача пользователю пойдёт через
  `copyMessage(chat_id, message_id)` — он не ломается, когда `file_id` протухает.
  `file_id` хранится рядом как кэш.
- **Дубли ловятся по `file_unique_id`** — он стабилен глобально, в отличие от
  `file_id`. Повторная заливка того же файла не создаёт вторую карточку, бот
  просто показывает существующую.
- **Фильм можно принять и как `document`** — mkv Telegram часто не распознаёт
  как видео.
- **Без `TMDB_API_KEY` мастер не ломается**, а сразу предлагает ручной ввод
  (`Название | Год | Описание`). То же самое, если TMDB не ответил.
- **Опубликовать фильм без названия нельзя** — бот объясняет, почему.
- **Редактор полей** доступен с карточки: название, год, описание, постер
  (присылается картинкой), жанры (переключаются нажатием). Работает и без TMDB.
- **Любая команда прерывает незавершённый ввод** — иначе из мастера не выйти.

### TMDB

Ключ берётся на themoviedb.org/settings/api, бесплатно. Поддерживаются оба
формата: v3-ключ (уходит параметром `api_key`) и v4-токен (уходит заголовком
`Authorization: Bearer`) — определяется автоматически.

## Каталог и поиск

```
🎬 Каталог
   ├─ 🆕 Новинки          постранично, по 8 фильмов
   ├─ 🎭 По жанрам        только непустые жанры, со счётчиком
   └─ 🎲 Случайный фильм
```

- Карточка открывается из списка, из поиска и по ссылке
  `t.me/бот?start=film_<id>`.
- Кнопка «Назад» на карточке возвращает **на ту же страницу списка** — адрес
  списка запоминается в сессии.
- Стрелки пагинации на краях не исчезают, а гаснут: иначе кнопки прыгают
  под пальцем.
- Поиск срабатывает на **любой текст** в чате, а не только после нажатия
  «Поиск»: человек, присылающий боту название, ждёт результат, а не подсказку
  про кнопки.
- Единственное совпадение открывается карточкой сразу, без промежуточного
  списка из одной строки.
- Каждый запрос пишется в `search_queries`, включая нулевые — это готовый
  список того, что стоит залить следующим.

## Доступ и выдача

Решение «можно ли смотреть» принимается **только** в `src/services/access.ts`.
Если проверок станет две, они рано или поздно разойдутся. Порядок такой:

```
админ                       → пускаем
активная подписка           → пускаем, без лимитов
гейт спонсоров пройден       → пускаем, но не больше FREE_VIEWS_PER_DAY в сутки
каналов спонсоров нет        → пейволл
```

Выдача (`src/services/delivery.ts`):

```
copyMessage(user, storage_chat_id, storage_message_id, protect_content: true)
   ↓ не вышло — пост в канале удалили?
sendVideo(user, file_id, protect_content: true)
   ↓
записываем просмотр + ставим сообщение в очередь на удаление
```

Порядок именно такой. `copyMessage` отражает текущее состояние канала и не
зависит от протухания `file_id`; `file_id` остаётся запасным путём, потому что
переживает удаление исходного поста.

**Автоудаление.** Очередь живёт в таблице `delivered_messages`, а не в памяти:
после перезапуска бота выданные фильмы всё равно исчезнут. Сборщик
(`src/jobs/delete-delivered.ts`) раз в минуту забирает всё, чему пора. Срок
задаётся `AUTO_DELETE_MINUTES`.

**Продление подписки прибавляется к остатку**, а не начинается заново:
оплативший заранее не должен терять оплаченные дни. Активная подписка у
пользователя всегда одна — прежние закрываются в той же транзакции.

### Выдача подписки вручную

```
/grant            — 30 дней себе
/grant 7          — 7 дней себе
/grant 30 12345   — 30 дней пользователю 12345
```

Команда видна только администраторам и остаётся полезной после запуска —
для решения вопросов поддержки.

## Гейт на каналы спонсоров

Бесплатный путь к фильму: подпишись на каналы партнёров — смотри. Это вторая
половина монетизации (первая — подписка) и главный источник трафика для
партнёрских каналов.

**Канал добавляется сам.** Сделайте бота администратором в канале партнёра —
он появится в «Админка → Каналы спонсоров» выключенным, а вам придёт
уведомление с кнопкой «Включить». Отдельной команды добавления нет намеренно:
без прав администратора Telegram не отдаёт статус подписчика, проверить
подписку нечем, и канал бесполезен. По той же причине канал автоматически
уходит из гейта, если бота разжаловали.

**Какие права дать боту в канале партнёра:**

| Право | Нужно? | Зачем |
|---|---|---|
| статус администратора | обязательно | без него `getChatMember` не отдаёт статус подписчика |
| «Пригласительные ссылки» | для приватных каналов и каналов с заявками | бот сам выпускает инвайт-ссылку; без этого права Telegram не присылает `chat_join_request` |
| публикация, удаление, закреп, управление участниками | не нужно | не давайте — партнёру спокойнее |

В канале-хранилище боту хватает голого статуса администратора: он там только
читает посты и копирует их. Telegram не даёт назначить админа без единого
права — включите «Публикация сообщений», остальное выключите.

**Как проверяется подписка.** `getChatMember(channel_id, user_id)`: пропускаем
`member`, `administrator`, `creator` и `restricted` с `is_member`. Проверка
идёт **при каждом запросе фильма**, а не один раз: половина людей отписывается
сразу после получения файла.

**Кэш — `SPONSOR_CACHE_SEC`, по умолчанию `0`.** Ноль означает «проверять при
каждом запросе фильма»: отписался от канала — доступ пропал сразу. Значение
больше нуля хранит успешную проверку в Redis (`ff:sponsor:<id>`) и экономит
запросы к API, но ровно столько же секунд после отписки фильмы ещё выдаются.
Один просмотр стоит не больше `SPONSOR_MAX_CHANNELS` вызовов `getChatMember`,
так что поднимать кэш стоит только на заметном трафике. Отказ не кэшируется
никогда: человек жмёт «Проверить» сразу после подписки и должен пройти
немедленно.

**Приватные каналы.** Если у канала включены заявки на вступление,
`getChatMember` отвечает `left`, пока заявку не одобрят. Поэтому бот ловит
`chat_join_request` и засчитывает саму заявку (`ff:join:<user>:<chat>`, неделя).
Для приватного канала без юзернейма бот при включении выписывает инвайт-ссылку
сам — для этого ему нужно право «Пригласительные ссылки».

**Если проверить не удалось** (бота выгнали, канал удалён) — пропускаем и пишем
`error` в лог. Держать людей в заложниках из-за чужой ошибки нельзя.

**Что настраивается в карточке канала:** название (его видят пользователи),
ссылка, срок размещения (начало и окончание, `ДД.ММ.ГГГГ`, окончание —
включительно), план по подписчикам. Если включённый канал всё равно не в гейте,
карточка прямо говорит почему: «ждёт начала размещения», «срок истёк»,
«нет ссылки».

**Счётчик для партнёра.** На пару «юзер + канал» приходится один зачёт
(UNIQUE в `sponsor_passes`), поэтому `joined_count` показывает людей, а не
клики, и годится как отчёт и основание для цены за место.

**Ограничения.** В гейте показываются первые `SPONSOR_MAX_CHANNELS` (по
умолчанию 3) включённых каналов — дальше люди просто уходят. Канал без
юзернейма и без инвайт-ссылки в гейт не попадает: подписаться на него
невозможно.

**Дневной лимит.** Прошедший гейт смотрит не больше `FREE_VIEWS_PER_DAY`
фильмов в сутки (окно скользящее, 24 часа). `0` — без ограничения.
На подписчиков лимит не распространяется — это и есть разница между
бесплатным и платным.

**Пока каналов нет, бесплатного пути нет** — показывается пейволл. Иначе
достаточно было бы выключить последний канал, чтобы раздать каталог даром.

## Статистика и рассылки

«Админка → 📊 Статистика»: пользователи и прирост за сутки, DAU, активные
подписки, заработок в звёздах (всего и за 30 дней), доля платящих, просмотры,
прохождения гейта, оплаченные приглашения. Числа берутся одним запросом —
иначе они относились бы к разным моментам времени и не сходились бы между собой.

Оттуда же два отчёта: **топ фильмов за 30 дней** и **«искали, но не нашли»** —
сгруппированные пустые запросы, то есть готовый список того, что стоит залить
следующим.

### Рассылка

«Админка → 📣 Рассылка». Три сегмента: всем, с подпиской, без подписки.
Забаненные не получают рассылку никогда.

Порядок такой: выбрали сегмент → бот показывает, сколько получателей → прислали текст
(HTML-разметка как в сообщениях бота) → увидели карточку с предпросмотром →
«🚀 Отправить». Текст не улетает сразу: между вводом и отправкой всегда есть шаг
подтверждения.

**Троттлинг — 60 мс между сообщениями** (около 16 в секунду). Telegram
пропускает примерно 30, и это общий лимит на бота: выбрать его рассылкой
значит поставить в очередь обычные ответы живым людям.

**Рассылка переживает перезапуск.** Получатели перебираются по возрастанию
`tg_id`, и последний разобранный лежит в самой рассылке (`last_user_id`).
После рестарта `resumeBroadcasts()` продолжает с того же места — никто не
получит сообщение дважды. Порядок по id, а не по времени захода, именно
поэтому: он не меняется под ногами, пока рассылка идёт.

**Остановить** можно на ходу — задача сверяет статус перед каждым сообщением.

### Пользователи

`/user <id>` — карточка: имя, ник, когда пришёл и заходил, кто пригласил,
подписка, сколько оплатил, скольких привёл. Кнопками: выдать 30 дней,
заблокировать или разблокировать. Забаненного бот игнорирует молча — это
решает `auth` ещё до всех обработчиков.

## Что держит бота в рамках

Инварианты, которые легко сломать незаметно — если правите код, держите их в голове.

**Пользователю доступно только опубликованное.** `getFilm()` фильтрует по
`is_published`, потому что id последовательные: без фильтра диплинк `film_<id>`
и кнопка «Смотреть» отдавали бы черновики перебором чисел. Админке нужен
`getFilmRow()` — он без фильтра, и трогать его не надо.

**Подпись к медиа не длиннее 1024 символов.** Переполнение — это не усечённый
текст, а отказ Telegram отправить карточку целиком. Считает `fitCaption()`:
экранирование раздувает текст (один `&` даёт пять символов), поэтому обрезаем
после экранирования и не разрубаем HTML-сущность пополам.

**Чужой текст в HTML-сообщении экранируется.** Название фильма пишет админ,
имя пользователя — сам пользователь; незакрытая угловая скобка ломает разметку
и сообщение не уходит вовсе.

**Секреты не попадают в логи.** Токен бота лежит в адресе каждого запроса к
Telegram, строки подключения — в тексте ошибок драйверов. Сериализатор ошибок
в `src/lib/logger.ts` вычищает и то и другое: логи хостинга приватные, но
токеном бот угоняется целиком.

**Платёжные апдейты идут мимо лимита частоты.** Отброшенный `pre_checkout_query`
это сорванная оплата.

**Команда сбрасывает незавершённый ввод.** Иначе следующий текст админа улетает
в поле, из которого он давно ушёл.

## Рефералка

Ссылка вида `t.me/<бот>?start=ref_<id>` — экран «🎁 Пригласить друга».

> Кнопка в главном меню сейчас закомментирована (`src/bot/keyboards/main.ts`).
> Сам экран и начисление работают — вернуть кнопку это одна строка. Оба получают по `REFERRAL_BONUS_DAYS` дней (по умолчанию 3).

**Бонус начисляется не за переход, а за первый просмотр приглашённого.** За
клик по ссылке платить нельзя — это накручивается пустыми аккаунтами за минуту.
Чтобы получить фильм, надо пройти гейт спонсоров или заплатить, то есть сделать
ровно то, ради чего человека и звали.

Защита от накрутки:

- один зачёт на приглашённого — UNIQUE на `referrals.invited_id`, сколько бы
  фильмов он потом ни посмотрел;
- реферер пишется только при первом заходе (`coalesce` в `upsertUser`) —
  перейти по второй ссылке и сменить пригласившего нельзя;
- самоприглашение отклоняется ещё в `auth`;
- `REFERRAL_DAILY_LIMIT` (по умолчанию 10) — сверх лимита приглашение
  **записывается с нулём дней**: факт виден в статистике, денег за него нет.

`REFERRAL_BONUS_DAYS=0` выключает механику целиком — экран остаётся, но
сообщает, что бонусы отключены.

## Фоновые задачи

Всё, что делается по расписанию, живёт в `src/jobs/` и запускается из
`startJobs()`. Планировщик простой: интервал, защита от наложения проходов
(если предыдущий ещё идёт, следующий пропускается) и остановка при shutdown.

| Задача | Как часто | Что делает |
|---|---|---|
| `delete-delivered` | минута | удаляет выданные фильмы, которым вышел срок |
| `expire-subscriptions` | 5 минут | снимает флаг с истёкших подписок и пишет об этом человеку |
| `subscription-reminders` | час | напоминает за 3 дня и за 1 день до конца |

**Почему не BullMQ.** Очередь с отдельным воркером здесь нечего делать:
состояние задач уже лежит в базе (`delivered_messages`, `subscriptions`) и
переживает перезапуск, а проход — это один запрос и цикл по результату.
Redis-очередь добавила бы процесс, конфиг и точку отказа, не дав взамен
ничего. К вопросу стоит вернуться на этапе рассылок: там нужен троттлинг,
ретраи и прогресс — вот тогда очередь оправдана.

**Напоминания срабатывают один раз на порог.** Отправленный порог пишется в
саму подписку (`last_reminder_days`), поэтому ежечасный проход ничего не
дублирует. Пороги перебираются от узкого к широкому: у кого осталось полдня,
получает напоминание «за 1 день», а не «за 3».

**Тихие часы.** С 21:00 до 10:00 по Москве напоминания не уходят — задача
просто пропускает проход. Сообщение об окончании подписки шлётся в любое
время: оно привязано к моменту, а не к нашему удобству.

**Автопродляемым не пишем.** Если подписка оформлена как Telegram Stars
Subscription, о предстоящем списании предупреждает сам Telegram; наше
«подписка заканчивается» только сбивало бы с толку. Флаг `auto_renew`
проставляется при оплате из `is_recurring`.

## Тарифы

«Админка → ⭐ Тарифы». Цена в звёздах, срок в днях и название меняются прямо
там; новый тариф заводится одной строкой вида `30 299` (дней и звёзд) и
создаётся выключенным — сначала проверьте, потом включайте.

Выключенный тариф исчезает из продажи, но оплаченные по нему подписки
продолжают работать до конца срока. Удалённый — тоже: у подписки и платежа
просто обнуляется ссылка на тариф, дни и деньги остаются на месте.

Автопродление Telegram привязано к периоду в 30 суток, поэтому кнопка
«с автопродлением» появляется только у тарифа с `days = 30`.

## Оплата (Telegram Stars)

Платим звёздами (валюта `XTR`). Никакого мерчанта и `provider_token` не нужно:
Telegram сам проводит платёж, бот получает звёзды на свой баланс и выводит их
через @BotFather.

```
[тариф — 299 ⭐]  →  sendInvoice(XTR, payload "sub:<plan_id>")
                        ↓ пользователь подтверждает
                     pre_checkout_query  →  проверяем, что тариф жив  →  ответ за 10 с
                        ↓
                     successful_payment  →  запись платежа + продление в одной транзакции
```

**Идемпотентность.** `payments.telegram_payment_charge_id` — UNIQUE. Telegram
повторяет апдейт, пока бот не ответит 200, поэтому `successful_payment` вполне
может прийти дважды; вставка по конфликту ничего не делает, и подписка не
продлевается второй раз. Запись платежа и выдача дней идут одной транзакцией —
не бывает оплаты без дней и дней без оплаты.

**pre_checkout_query нельзя проморгать.** Ответ нужен за 10 секунд, иначе
Telegram отменяет платёж, поэтому в обработчике ровно один запрос в базу.
По той же причине платёжные апдейты проходят мимо лимита частоты
(`src/bot/middlewares/rate-limit.ts`): отброшенный апдейт — это сорванная оплата.

**Автопродление.** Месячный тариф дополнительно предлагается как подписка
Telegram с автосписанием. Такой счёт выпускается только через
`createInvoiceLink` с `subscription_period` — у `sendInvoice` этого параметра
нет. Период возможен один: 2 592 000 секунд (30 суток), поэтому кнопка
появляется только у тарифов с `days = 30`. Отключается `STARS_AUTO_RENEW=false`.
Если Telegram откажет в выпуске ссылки, бот молча выставит обычный счёт —
человек не должен остаться без возможности заплатить.
Отменяет подписку сам пользователь: Настройки → Мои звёзды → Подписки.

**Возврат** (только админ, в течение 21 дня):

```
/payments        — последние платежи, оттуда берётся charge_id
/payments 12345  — платежи конкретного пользователя
/refund <charge_id>
```

Сначала просим Telegram вернуть звёзды и только потом правим базу: если запрос
не прошёл, у пользователя не должно остаться ни снятой подписки, ни пометки о
возврате. Вместе с деньгами снимаются и оплаченные дни — иначе подписка
осталась бы бесплатной.
